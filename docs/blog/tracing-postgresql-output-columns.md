# Where did that column come from? Ten fixes in postgres-viz

Suppose you're about to rename a column. You open a postgres-viz snapshot, select the column, and find a function listed as a reader. The function contains the right name. Did it actually read your column? A nested query can give its own result the same name, sometimes without an `AS` anywhere in the SQL.

When postgres-viz scans a SQL routine, the parser gives it a syntax tree. The analyzer then builds a list of visible columns at each query level. Each entry needs a name that the surrounding query can use, plus the underlying column reads that explain its value. Losing the name can produce a missing-reference warning. If a column with that name exists in an outer query, the same mistake can silently attach the reference to the wrong place.

These ten fixes are in the development checkout after v0.11.0. Each query below runs independently, without a sample database. We ran all ten as SQL functions on PostgreSQL 16, checked the results shown here, and scanned them with the updated CLI. The snapshot contained no warnings or unresolved references.

## Following a name through a SELECT

### 1. An inner NULLIF can hide an outer column

```sql
SELECT (SELECT "nullif" FROM (SELECT NULLIF(1, 2)) AS q)
FROM (VALUES (99)) AS audit("nullif");
```

The result is `1`. PostgreSQL labels the inner expression `nullif`, so the outer value `99` never enters the calculation. The old analyzer left the inner label empty and looked one query level farther out. In a routine with a real `audit` table, that produced a false read of `audit."nullif"`. The fix recognizes the parser's special `AEXPR_NULLIF` operator and assigns its output name while still walking both operands for column reads.

### 2. Taking an array element keeps the array's name

```sql
SELECT q.samples
FROM (
  SELECT samples[pos]
  FROM (VALUES (ARRAY[3, 7], 2)) AS s(samples, pos)
) AS q;
```

The result is `7`. Inside `q`, PostgreSQL reads both `samples` and `pos` but names the output `samples`. The analyzer used to find the reads inside the brackets and still report the outer reference as missing. It now follows the subscripted expression to recover the name and walks the index expression separately for dependencies. This matters when a routine gets its array and index from different table columns.

### 3. A scalar subquery exports its single column's name

```sql
SELECT q.n FROM (SELECT (SELECT 7 AS n)) AS q;
```

The result is `7`. The innermost `SELECT` explicitly names its column `n`. The middle `SELECT` projects a scalar subquery, and that result carries the name one level farther. Previously, postgres-viz recorded reads inside the subquery but lost the name at that boundary. It now reuses the analyzed result when the scalar subquery has one known output column. ## Building the row the outer query sees

### 4. XMLTABLE declares a relation inline

```sql
SELECT x.n
FROM XMLTABLE('/r' PASSING XML '<r>8</r>'
              COLUMNS n integer PATH '.') AS x;
```

The result is `8`. The declaration `COLUMNS n integer` is enough for PostgreSQL to resolve `x.n`. Looking in the catalog for a table named `x` would get us nowhere. The old analyzer skipped the declaration. It now builds a relation from the listed columns and applies the alias. If `PASSING` takes a real table column, the scan also records the routine's read of that XML document.

### 5. CASE can inherit a name from ELSE

```sql
SELECT q.fallback
FROM (
  SELECT CASE WHEN true THEN picked ELSE fallback END
  FROM (VALUES (7, 99)) AS s(picked, fallback)
) AS q;
```

The result is `7`, in a column named `fallback`. The `THEN` branch supplies the value here, while the `ELSE` column supplies the implicit name. The analyzer previously skipped `CASE` when naming outputs. It now handles the default label `case` and checks whether the `ELSE` expression supplies a stronger name, such as a column identifier. An explicit `AS` still takes precedence.

### 6. A generate_series alias can name its output column

```sql
SELECT g.g FROM generate_series(8, 8) AS g;
```

The result is `8`. The first `g` names the range in `FROM`. The second names the single column returned by this built-in scalar function. Previously, the analyzer recognized that output shape only in the path for `WITH ORDINALITY`, so it marked `g.g` as missing here. Both forms now use the same function-output logic. A captured user-defined overload keeps the analyzer from assuming the built-in shape for an unqualified call. [Range function tests](../../internal/analysis/from_scope_test.go)

## Outputs generated by a query

### 7. EXISTS has a boolean column named exists

```sql
SELECT q."exists" FROM (SELECT EXISTS (SELECT 1)) AS q;
```

The result is `true`. Unlike the scalar subquery in example 3, `EXISTS` supplies its own output name. The old analyzer walked the inner query but missed that name. It now recognizes the `EXISTS_SUBLINK` syntax node. In a routine that tests `EXISTS (SELECT 1 FROM orders WHERE total > 0)`, the outer boolean resolves and the predicate's read of `orders.total` survives.

### 8. A recursive CTE grows columns after its SELECT list

```sql
WITH RECURSIVE r(n) AS (
  VALUES (1) UNION ALL SELECT n FROM r
)
SEARCH DEPTH FIRST BY n SET visit
CYCLE n SET seen USING path
SELECT cardinality(visit), cardinality(path)
FROM r WHERE seen;
```

The single result row is `(2, 2)`. The recursive step repeats `1`. PostgreSQL marks that second visit and stops expanding the cycle. The CTE declares one ordinary column, `n`, but `SEARCH` adds `visit`, and `CYCLE` adds `seen` and `path`. The analyzer previously marked the output width as uncertain and missed the generated names. It now adds those names after applying aliases to the ordinary columns. When it can identify the traversal key's source, it can follow a reference to the generated path back to that key. [Recursive query tests](../../internal/analysis/routine_test.go)

### 9. CURRENT_DATE names a column without reading one

```sql
SELECT q.current_date = CURRENT_DATE
FROM (SELECT CURRENT_DATE) AS q;
```

The result is `true` on any date. PostgreSQL represents `CURRENT_DATE` as a SQL value expression. There is no function-call identifier to copy and no table column to look up. The old scan reported `q.current_date` as missing. The analyzer now derives the output label from the SQL value operation itself, which lets the outer reference resolve without adding a database-column dependency.

### 10. An ARRAY subquery supplies its own name

```sql
SELECT q.array FROM (SELECT ARRAY(SELECT 7)) AS q;
```

The result is the one-element integer array `{7}`. A bracket constructor such as `ARRAY[7]` and a query constructor such as `ARRAY(SELECT 7)` have different syntax-tree nodes. The analyzer already knew the bracket constructor's label. Recognizing the array subquery gives the second form its PostgreSQL name, `array`, while preserving the reads performed by the inner query. Previously, the snapshot listed `q.array` as missing. [Output-name inference](../../internal/analysis/scope.go)

## Checking the graph against the database

A passing SQL query establishes the server's interpretation. To catch a dependency bug, the tests also need to inspect the graph. The live fixtures create routines backed by real columns, execute them, capture a snapshot, and compare its references with the expected column reads. The `NULLIF` case shows why both checks matter. The routine can return the right number every time while a bad snapshot still tells you that renaming an unrelated column will affect it.
